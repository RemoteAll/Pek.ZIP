## 2026-11-19（十）真实平台联调打通，并修掉两个真 bug（TOFU 验签 / 缓存签名悬垂指针）

### 用户原话

> 请继续

### 平台侧状态变了：已批准，真实全链路首次跑通

之前一直卡 `AuthPending`，这次直接 `zpk sync` 就成功了（exit 0），三个数据集全部落盘并查询正确：

```
[pek-zip] 已安装 ip2region-v4 2026.10 → .zig-cache\livebasetest\Data/IpCache\ip2region-v4\2026.10
[pek-zip] 已安装 geolite2-city 2026.10 → …

```

平台目录实测：`/components/catalog.json` = **87,152 B**，`/components/catalog.json.sig` = **88 B**（标准 base64 带填充）。

### bug 1：`PubKey` 留空 = 完全不验签，TOFU 形同虚设（安全）

- 现象：`src/manager.zig` 两处验签判断都是 `if (self.cfg.pubkey.len > 0)`，而配置模板/README 写的是
  「留空 = 注册时从平台响应学习公钥并落盘固定（TOFU），**不需要每个应用都配**」。
  即：默认配置下 `catalog.json` **根本不验签** → 中间人改目录 + 换包即可绕过（包哈希来自未验签的目录，等于没有保护）。
- 修复：新增 `Manager.catalogVerifyKey()`——**配置的 `PubKey` 优先，留空时用注册时 TOFU 学到的平台公钥**；两处验签（目录 + 本地缓存）都改走它。
  `zpk status` 如实显示来源：`(留空：用注册时 TOFU 学到的平台公钥强制验签)`；错误文案也带「公钥来源」。
- 实测：`zpk sync --force`（`PubKey` 仍留空）**exit 0**，说明平台签名确实能被 TOFU 公钥验过（否则会报 `组件目录签名校验失败`）。
- 单测 `目录缓存验签：留空 PubKey 时用 TOFU 学到的平台公钥`：正确签名 → 缓存可用；改正文不动签名 → 返回 null 触发联网重拉。

### bug 2：缓存里的签名是悬垂指针 → 目录 TTL 直接失效（省流量白做）

- 现象：第二次 `zpk sync` 每次都打印 `本地目录缓存签名校验失败：BadSignature，改走联网刷新`。
- 取证：`python` 对比缓存与平台字节 —— body 完全一致（87,152 B，SHA256 相同），**但缓存里的 `.catalog.sig` 是 88 个字节的 `U`（`b'UUUU…'`）**。
- 根因：`sig_text` 指向 `sig_response.body`，而 `defer sig_response.deinit(self.gpa)` 写在 `if` 块内、**块结束就释放**，
  随后 `writeCatalogCache(..., sig_text)` 把已释放内存写进缓存（`0x55` 填充）。
- 修复：验签通过后 `sig_text = try arena.dupe(u8, sig_text.?)`（注释写明原因）。修复后缓存 `.catalog.sig` = `wXcQAQ==`（与平台一致）。
- 实测：修复后 `zpk sync` 走缓存——`复用本地组件目录缓存（…，新鲜期 3600s）`，无 `BadSignature`，不再每次白拉 85 KB 目录。
- 这条也说明：**「配了验签」不等于「缓存可用」**，验签失败是静默降级（改走联网），不看日志根本发现不了流量白花。

### 验证与基线

- 单测 **65/65**（新增 1 项）；`tools/regression.ps1` 的 `MinTests` **64 → 65**（只抬不降）。
- 升级链路端到端 `tools/verify-sync-e2e.ps1` 断言 **5 → 6 项**，新增 `catalog-cache-reused`（第三次 sync 必须命中缓存且无 `BadSignature`），实测 6/6 PASS、退出码 0。
- 坑：`e2e` 里不能用中文做断言——PS 5.1 管道会把子进程 UTF-8 中文按 ANSI 解码成乱码；断言一律用 ASCII 标记（`3600s` / `BadSignature`）。

### 仍开着的缺口

- **RAgent 代下载 IP 库**（用户提过「如果服务器有安装 RAgent，是不是可以检测并通过本机安装的 RAgent 来自动获取 IP 库」）：
  需要新增跨仓库协议（RAgent 侧做缓存 + 分发），本轮未做；当前各进程直接连平台、靠共享 `CacheDir` 避免重复下载。

## 2026-11-19（九）端到端验证：平台发新版 → 下载 → 安装 → 查询生效

### 用户原话

> 请继续

### 为什么做这一节

单测只覆盖到 `installZip` 层面，**「平台发新版 → 客户端自动发现 → 下载 → 安装 → 查询真的用上新数据」这条链从未端到端跑过**
（真实平台一直卡在 `AuthPending`，走不到目录下发）。所以造了一个本地假平台把这条链完整跑一遍，并固化成可重复脚本。

### 做法（`tools/verify-sync-e2e.ps1`，无需外网）

1. 用 `zpk mkxdb` 造两版 xdb：v1 `CN|Jiangsu|Nanjing|telecom|CN`、v2 `CN|Guangdong|Shenzhen|mobile|CN`；
2. `Compress-Archive` 打成 `ip2region-v4-2026.10-any.zip` / `...-2026.11-any.zip`，取 SHA256 写进 `catalog.json`；
3. `Config/Ip.toml`：`StoreUrl = http://127.0.0.1:<空闲端口>`、`CatalogMaxAge = 0`（每次都拉目录）、`AutoEnroll = false`；
4. 起 `python -m http.server` 当平台；第一次 `zpk sync` 期望装 2026.10；
5. 把 `catalog.json` 换成 2026.11，再 `zpk sync` 期望发现新版本并安装；
6. `zpk lookup 114.114.114.114` 期望返回 **Guangdong Shenzhen**（不是 v1 的 Jiangsu Nanjing）。

### 实测结果（PASS 5 / FAIL 0，脚本退出码 0）

```
PASS  install-v1            2026.10 installed by first sync
PASS  upgrade-to-v2         2026.11 installed by second sync
PASS  clean-old-version     2026.10 removed (keep = 1)
PASS  detect-newer          second sync mentions 2026.11
PASS  lookup-uses-new-data  lookup returns v2 region (Guangdong), not v1 (Jiangsu)
=== RESULT: PASS (fail=0) ===
```

### 过程中的两个坑（脚本已内置防护）

- **残留服务串台**：上一轮没杀干净 `python -m http.server`，端口仍被占，新脚本 `Start-Process` 失败但「就绪探测」却打到了**旧服务**（目录里是 2026.11 的目录），
  于是第一次 `sync` 直接装了 2026.11，`install-v1` 断言假失败。修法：启动前 `Get-NetTCPConnection` 找空闲端口 + 先杀该端口上的监听进程，
  结束时按端口再杀一次（比只 kill `Start-Process` 句柄可靠）。
- **PS 5.1 把外部程序的 stderr 当终止错误**：`$ErrorActionPreference='Stop'` 下 `zpk` 往 stderr 写一行进度就炸脚本（老坑，脚本用临时 `Continue` 包装）。
- **`keep_versions = 1` 会删旧版**：升级后 `2026.10` 目录**必然消失**，断言要按「新版本在、旧版本不在」写，不能反过来。

### 口径说明

- `zpk sync` 退出码在假平台上为 **1**：假目录只发了 4 个数据集里的 1 个（geolite2-city/asn 与 ip2region-v6 报「组件目录里没有…」），
  与本验证要证明的链路无关；脚本按断言判定成败，并在输出里注明。
- 这个脚本**不进 `regression.ps1`**：它依赖 `python` 与本地端口，属"发布前手工验证"，一键回归保持纯 Zig 零外部依赖。

## 2026-11-19（八）省流量与升级能力核对：补上「常驻进程自动更新」

### 用户原话

> 目前的方案是可以省流量也可以升级最新的吧。

### 核对结果

**省流量：成立**（四条都有实测/代码依据）：
1. `CatalogMaxAge`（默认 1h）目录 TTL：新鲜期内不联网（实测「复用本地组件目录缓存」且无网络错误）；
2. `ensureAll` 在**本地齐全且非 check_updates** 时直接 return —— 启动不联网；`zpk sync` 才比对版本，
   且 `compareVersions(远端, 已装) != .gt` 一律跳过；
3. 同机 `.sync.lock` 独占创建，只有一个进程去下，其余复用共享 `CacheDir`；
4. 下载在后台线程，查询不受影响。

**升级到最新：原来只成立一半** —— `zpk sync` / `sync --force` 能发现并安装新版（装完 `cleanOldVersions` 只留 1 版），
但**常驻进程没有任何周期性检查**：它只在启动那一次跑 `ensureAll`，之后外部下好的新版它感知不到。
这条本轮补上。

### 本轮改动

- `Config.AutoUpdateMinutes`（TOML）+ `StartOptions.auto_update_minutes`（`?u32` 覆盖，`0` = 关闭）。
  默认 **0（关闭）**——按「新增周期任务前先算账」的口径，不默认开。
- `workerMain`：首轮照旧（补缺 → 重建 → 发布 → `finished`），之后若开启则循环
  「可被唤醒的等待 → `syncPass(true)`」；`syncPass` 在**没有新版本时不重建定位器**（省一次全量打开）。
- 等待用 `Io.Condition.waitTimeout`（不是 sleep 轮询），`destroy()` 置 `stop` + signal → **立即退出，不等满间隔**。
- **`waitIdle()` 语义修正**：原来 join 线程，开启定时更新后会永久阻塞；改为等「首轮完成」（`finished` + `ready_cond`），
  线程回收挪到 `destroy` 内的 `joinWorker()`。
- `zpk selfcheck` 增加「定时检查 : Nmin（0 = 关闭）」。

### 带宽账（开启后每轮开销）

一轮 = 1 次 `catalog.json` GET（≈85 KB，且受 `CatalogMaxAge` 约束，TTL 内走本地缓存 → 0 字节），
新版本才下包（4~7 MB，几天一次）。按 360 分钟、TTL 3600s 算：**每天最多 4 × 85 KB ≈ 340 KB**，
远低于「每分钟累计 1 MB」的门槛。

### 验证

- 新增用例「定时检查更新：destroy 能立即叫停等待中的后台线程」：
  `auto_update_minutes = 60` 启动 → `waitIdle()` 首轮返回 → `destroy()` 实测 < 3s 退出（不会等 60 分钟）。
- `zig test src/root.zig` → **All 64 tests passed**；回归下限 63 → 64。
- 踩坑：配置里 `StoreUrl = ""` **不会**置空（`applyToml` 对空值保持默认），测试差点打到真实平台；
  改用 `http://127.0.0.1:1` 保证确定性失败。


## 2026-11-19（七）复用调研：zzig 公共方法哪些能用、哪些不能用

### 用户原话

> 请继续，看有没有可提取和复用zzig中公共方法

### 调研结论

| zzig 能力 | 判断 | 依据 |
|---|---|---|
| `http.fetchBytesWithTimeout`（`io.concurrent` + `Future.cancel`） | ✅ **已复用**（上一轮） | 同版本 0.17.1，且已在 zzig 上线验证 |
| `fsio.writeFileAtomic` / `replaceFile`（`.tmp` + 替换） | ✅ **本轮采纳** | 见下「本轮改动」 |
| `net/socket_timeout.setRecvTimeout`（SO_RCVTIMEO） | ⏭ 不适用 | socket 由 `std.http.Client` 内部持有，我们拿不到句柄；自己接管连接又会绕开它的重定向/连接池 |
| `crypto/hash_util.sha256Hex / hexLower / constantTimeEql` | ⏭ 不采纳 | 我们要的是**流式**算文件 SHA-256（`store.sha256FileHex`），`std.crypto` 已够；为 3 行工具函数引入整包依赖不划算 |
| `archive/zip.Reader` | ⏭ 不采纳 | `std.zip.extract` 已拒绝绝对路径与 `..`，替换无收益 |
| `json` / `config` / `file` / `logs` | ⏭ 不采纳 | 本项目是薄实现（std.json / 手写 key=value），引入整包抽象收益不成比例 |
| **整包 `b.dependency("zzig")`** | ❌ 不可行 | zzig 的 `build.zig.zon` 依赖本地路径 `../lighting`；独立仓库的 Pek.ZIP 绑这个路径，换台机器就编不过 |

### 本轮改动（采纳 fsio 的原子写口径）

- 新增 `src/fsutil.zig`：`writeFileAtomic`（写 `<path>.tmp` → `replaceFile`）与 `replaceFile`
  （语义与 zzig `fsio` 一致：Windows 覆盖必须先删目标再 rename；父目录自动创建）。
- 接入三处**坏了会出人命**的写入：
  - `auth.zig` 的 `install.id` / `client.key`：被截断 → 身份丢失 → 平台侧要重新审批授权；
  - `auth.zig` 的 `pubkey.txt`（TOFU 固定平台公钥）：截断 → 下次启动当非法身份；
  - `config.zig` 首次生成的 `Config/Ip.toml`：截断 → 配置回退默认值。
- 目录缓存（`.catalog.*`）暂未改：坏了只是多拉一次，且它是「省带宽」的优化，不引入额外风险。

### 验证

- 新增单测「原子写：覆盖已有内容且不留 `.tmp` 残留」；`zig test src/root.zig` → **All 63 tests passed**；回归下限 62 → 63。
- 过程中踩到的两个坑：`writeFileAtomic` 起初让调用方传 arena，测试里传的是 GPA → **临时路径泄漏**被 testing.allocator 抓到；
  改成由函数内部 `defer gpa.free(tmp_path)`。另外 tmp 与目标同目录，父目录不存在时得先 `createDirPath`。


## 2026-11-19（六）真实场景调优：国内 IP 不再白付 MMDB 的 1.5 µs

### 用户原话

> 你要联网结合实际应用场景做分析，看是否有其他可以调优的。我的需求不一定就是OK的，你应该比我更清楚了解才是。

### 联网查到的参照（ip2region 官方 Rust binding README，仓库内 benchmark）

| 模式 | 内存 | IPv4 | IPv6 |
|---|---|---|---|
| No Cache（每次按偏移 seek） | 1–2 MB | 54 µs | 122 µs |
| Vector Index Cache | 1–2 MB | 27 µs | 100 µs |
| Full Cache（整文件读进内存） | 20 MB / 200 MB | 120–139 ns | 178 ns |

官方 full-cache 实测 avg 167 ns（v4）/ 281 ns（v6）。
**我们的 mmap + 文件内 Vector Index 是 45 ns/op** ——比它们的 full cache 还快（不用拷贝、共享 page cache、多进程零额外内存），
所以「读 xdb」这一层没有优化空间，不用改。

真正的浪费在**合并逻辑**：国内 IP 也已经命中 ip2region（省市/ISP 齐了），却还去查一次 MMDB 只为补经纬度/时区/区县，
而 MMDB 单次 1552 ns，是 xdb 的 **35 倍**。中文场景流量以国内为主，这笔钱占整体耗时 ~95%。

### 做法

- `Locator.Options{ skip_world_for_china = false }` + `lookupOptions(...)`：命中 ip2region 国内记录时跳过
  MMDB（世界库与 ASN 库都跳过）。**默认 false，行为不变**；国外 IP 完全不受影响。
- `Manager.StartOptions.skip_world_for_china` 透传，CLI 对应 `zpk lookup --fast`。
- 基准新增对比项，并把样例 IP 换成国内段（114.114.0.0/16，江苏），否则测不出真实业务差异。

### 实测（ReleaseFast，20 万次/项，真实数据）

| 场景 | ns/op | QPS |
|---|---|---|
| xdb（ip2region v4） | 44.9 | 22.3 M |
| MMDB（国外库） | 1552.6 | 644 k |
| 合并 lookup（默认） | 1765.4 | 566 k |
| **合并 lookup（国内快路径）** | **186.6** | **5.36 M** |
| 保留地址短路 | 9.8 | 101.8 M |
| 4 线程并发 lookup | 470.8 | 2.12 M |

→ 国内查询 **9.5×**（1765 → 187 ns）。代价明确写在类型注释里：拿不到经纬度/时区/区县/ASN。

### 顺带确认（不做的）

- **不做内存索引/整文件缓存**：mmap 已快于官方 full-cache，且零拷贝、多进程共享，加了只会多占内存。
- **不默认打开快路径**：会静默丢字段，必须是显式选择。


## 2026-11-19（五）超时改用原生方案：复用 zzig 的 `io.concurrent + Future.cancel`

### 用户原话

> 我记得wukong-lite中原本也实现有看门狗，后面取消了看门狗用了原生的某个方式，你看一下怎么复用，或者直接看zzig中是否有可以直接复用的，我记得http这个zzig中是有的。

### 核对结果

- `G:\Code\Zig\WuKong-Lite` 是 **Python** 工程（`.venv` / `urllib3`），它的“看门狗 → 原生”是 Python 侧的经验，Zig 里不能直接复用。
- `G:\Code\Zig\zzig`（`minimum_zig_version = "0.17.1"`，与本项目同版本）里 `src/http/http.zig` 有
  **`fetchBytesWithTimeout`**：`io.concurrent(fetchWorker, ...)` → 轮询 `ResponseResult.completed` →
  超时 `future.cancel(io)` → 返回 `error.RequestTimeout`。这就是用户说的“原生方式”，且已上线验证。

### 据此改造（去掉上一轮自造的 detached 看门狗）

- `std.Io.concurrent(io, worker, args)` 起任务，`Future.cancel(io)` 请求取消**并等任务结束**（内部 join），
  因此**不会遗留线程**（上一轮 detach 写法在真卡死时会漏一个线程）。
- 等待方式比 zzig 更进一步：不用轮询 + `sleep`，改用 `Io.Condition.waitTimeout`（事件驱动，超时才唤醒）。
- 因为 `cancel/await` 保证把任务收回，Job 里的 url/payload/headers/out_path 可以**直接借用调用方切片**，
  不必再堆分配 + 复制 + 自毁；直接用调用方已有的 `*std.http.Client`，不再每次重建客户端（省一次根证书 rescan）。

### 验证（实测）

- 端到端：本地「只 accept、不回包」监听 + `HttpTimeoutMs = 1200` → `zpk sync` **1.25s** 返回 `Timeout`。
- `zig test src/root.zig` → **All 62 tests passed**（超时用例改为验证「40ms 上限 vs 300ms 任务，调用方未被拖住」）。
- 顺手踩到的坑：用 `Set-Content -Encoding utf8` 写测试配置会带 **BOM**，导致首行 `StoreUrl` 解析失败、
  回落到默认平台地址（差点把“本地超时验证”跑成“真实平台请求”）；造配置一律写**无 BOM** UTF-8。


## 2026-11-19（四）请求超时：核对 Zig 0.17.1 源码后自己实现

### 用户原话

> 我记得是有超时的吧，zig的你要分析一下ziglang0.17.1的源码

### 源码核对结论（逐行看 `lib/std`，不是猜）

| 论点 | 源码位置 | 结论 |
|---|---|---|
| `Io.net.ConnectOptions.timeout` 存在且**生效** | `Io/net.zig` `ConnectOptions{ mode, protocol, timeout }` → `io.vtable.netConnectIp(io, address, options)`，`ConnectError` 含 `Io.Timeout.Error` | ✅ 底层连接真支持超时 |
| `Socket.sendTimeout / receiveTimeout` 存在且生效 | 同上，内部走 `io.operateTimeout(.{ .net_send/.net_receive }, timeout)` | ✅ 收发也支持 |
| `std.http.Client.ConnectTcpOptions.timeout` | `http/Client.zig` 声明了该字段，但 `connectTcpOptions` 函数体**从未读取**；内部 `host.connect(io, port, .{ .mode = .stream })` 把超时丢掉了 | ❌ **死字段** |
| HTTP 层有无其它超时 | 整个 `Client.zig` 里 `timeout` 只出现 1 次（就是上面那行）；`RequestOptions` 没有 | ❌ 无 |
| 能否用 `Io.operateTimeout` 补连接 | `Io.Operation` 只有 file_read/write、device_io_control、net_receive/send/read/write，**没有 net_connect** | ❌ 补不了 |
| 能否用任务超时 | `Io.Future.await/cancel` 无 timeout 参数，且注释写明 "Not threadsafe"；`Group.await` 同样无超时 | ❌ 无 |

**所以用户的记忆是对的、我的上一轮判断是错的**：Zig **确实有**超时能力（`Io.Timeout` + `Io.Mutex/Condition.waitTimeout` + socket 层 timeout 变体），
只是 `std.http.Client` 这一层**没接上**（`ConnectTcpOptions.timeout` 是死字段）。上一轮写"std 0.17 的 Client 未暴露 per-request 超时"结论方向对、依据不完整，此处更正。

### 做法（`src/http.zig`）

- 请求跑在**独立工作线程**（Job 槽堆分配、自建 `std.http.Client`，绝不引用调用方栈），
  主线程用 `Io.Condition.waitTimeout` 等到 `HttpTimeoutMs`，到点返回 `Error.Timeout` 并 `detach` 该线程
  （它结束后自行释放槽位，不 join、不阻塞调用方）。
- 新增配置 `HttpTimeoutMs`（默认 120000ms，0 = 不限），`zpk selfcheck` 里可见。
- 失败文案区分：`Timeout` 给出「超过 HttpTimeoutMs 未响应…可调大 Config/Ip.toml」，
  与普通 `TransportFailed`（确认平台地址/网络/证书）分开，不再混用。
- 顺手踩到的 0.17 事实：`std.Thread.Mutex/Condition` 已移除（改用 `std.Io.Mutex/Condition`）；
  `std.time.nanoTimestamp` 已移除（改用 `Io.Clock.real.now(io).nanoseconds`）；
  `Io.Timeout.duration` 要的是 `Clock.Duration{ raw: Io.Duration, clock }` 而不是 `Io.Duration`。

### 现象与根因（实测，不猜）

`zig build test` 长时间无输出、`test.exe` 持续吃 CPU（实测 +14.8s CPU / 5s 墙钟，内存仅 7MB）。
用 `Start-Process` 把 stderr 落盘才看到进度停在 **28/59 `qqwry_writer.test.CSV → 纯真格式 → 读回`**。

逐个用诊断打印缩小到 `convert()` 的 CSV 读循环，最后一个空行之后 `loop` 计数一路涨到 12 万+：

- `std.Io.Reader.takeDelimiterExclusive` 在**真正 EOF** 处会反复返回 **0 长度切片**（不是 `error.EndOfStream`），
  原代码 `line.len == 0 → continue` 于是无限空转。改为 `takeDelimiter`（返回 `?[]u8`，EOF 返回 null）。
  —— 这条是"`zig build test` 卡住"的唯一根因。

修掉死循环后暴露出后面两处此前被掩盖的真实缺陷（都不是测试写错）：

1. **数据区偏移漏算 4 字节**：`before` 取在写 `end_ip` 之后，`data_offset` 每条只累加「区域串+2×0x00」，
   于是第 2 条起索引偏移整体前移 4B，读回的 `end_ip` 落在上一条区域串尾部 → 除第一条外全部查不到。
2. **末条记录空地址段落在文件末尾**：`readAddress` 必读 u32，只剩 1 个 0x00 时直接判 `Corrupt`。
   真实库里最后一条就是这种形态，属于合法数据 → 不足 4 字节时按普通 NUL 结尾串读。
3. 顺带：首行 DB-IP 表头（`start_ip,...`）原先按"解析失败"计入 `skipped`，指标失真 → 表头跳过且不计数。

另外用例本身有个 Windows 限制陷阱：第二次 `convert` 复用同一个输出路径时，前一个 `QqwryReader`
仍持有该文件 mmap，`createFile` 直接 `USER_MAPPED_FILE → AccessDenied`（表现为 `FAIL (WriteFailed)`）。
用例改用独立输出文件——这不是放宽断言，而是原写法在 Windows 上根本不成立。

## 2026-11-18 立项目：Zig 版 IP 库（Pek.ZIP）

### 用户原话

> 帮我参考 `G:\Code\Rust\Pek.IP` 和 `G:\Code\Pek.FrameWork\DH.NIP` 这两个项目使用 ziglang 实现功能，同样要考虑性能以及根据全局用户指令做接续相关

> IP文档我还是想直接通过RPanelSever中的资源来在启动时异步判断是否存在，不存在就下载

### 背景

- Rust `Pek.IP` 已覆盖 xdb v3 + MMDB + 合并 + 组件源按需下载（Ed25519 + SHA-256 + 自动注册票据）。
- C# `DH.NIP` 覆盖纯真 `ip.gz`（GBK）+ 在线 API 多格式解析 + DB-IP CSV→纯真格式转换。
- 生态里已有 Zig 项目（`Pek.ZPermissions` 等）与接续基建模板，可直接装备。

### 决策

1. **范围（v0.1）**：xdb v3（v4/v6、Vector/BTree）、MMDB（City/Country/ASN/ISP）、纯真 QQWry（gzip + GBK）、特殊地址分类、双源合并、CLI、基准、启动异步下载管理。
2. **数据视图统一到 `Blob`**：xdb / mmdb / qqwry 三种格式都需要「整文件只读字节」，mmap/堆/借用与生命周期只写一份（`src/blob.zig`）。第二个副本出现即违规。
3. **零分配查询是硬口径**：`XdbReader.lookup` / `MmdbReader.lookupWorld|lookupAsn` / `Locator.lookup` 返回借用切片；QQWry 的 GBK→UTF-8 写调用方 `Scratch`。Rust 版返回 `String`，Zig 版在热路径上省掉全部分配。
4. **mmap 而非全量读入**：`File.createMemoryMap`（Zig 0.17 的 std 已跨平台实现，Windows/POSIX 都有；`no_mmap` 可退化）。v6 库 37 MiB 不进进程私有内存，多进程共享页缓存。
5. **启动异步 = 本地同步 + 后台线程 + 原子热替换**：
   - `Manager.start` 只做 mmap（毫秒级），立刻可查（哪怕一个库都没有：内网/保留地址照常识别）；
   - 缺失数据集在**后台线程**拉取（catalog → 选包 → 下载 → SHA-256 → 解压 → 安装 → 重建 → swap）；
   - 读方**不取锁**（原子加 + 指针复核）；被替换的旧定位器进「退休列表」，运行期不销毁，`destroy()` 统一回收 —— 这是 hazard pointer 的廉价替代，避免读者 use-after-free；
   - 选线程而非 await 的原因：std 0.17 在 Windows 上 socket 读是同步 `deviceIoControl`，真异步要自建 AFD/IOCP；接口保持可替换（POSIX 可换 `Io.concurrent`）。
6. **安全默认值**：配了 `PubKey` 但 Ed25519 验签未实现 → **拒绝下载**并在 `lastError()` 说明（不静默放行）；`StoreUrl` 为空 = 仅本地缓存；`DownloadV6=false`。
7. **GBK 码表用生成物**：`tools/gen_gbk_table.ps1`（.NET CP936）生成 `src/gb2312.bin`（24066×u16，48 KiB）；用二进制 + `@embedFile` 而不是 2.4 万行 Zig 字面量（源码瘦、编译快）。反向编码器运行时排序一次，供后续 CSV 转换用。
8. **接续基建全套装备**：`.github/copilot-instructions.md`、`docs/{项目接续指南,用户档案,项目记忆,决策记录}.md`、`tools/continuity/*`（从 `Pek.ZPermissions` 字节级复制）、`.vscode/tasks.json`（打开项目自检）、`tools/regression.ps1`。
9. **CLI 默认离线**：`zpk lookup` 默认只读本地（`background=false`），避免「平台不可达导致命令行卡住」；要演示启动异步用 `--online`（后台补缺 + 等下载结束再退出），批量部署用 `zpk sync`。
